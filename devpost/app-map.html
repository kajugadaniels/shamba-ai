From garden idea to saved evidence

One small outdoor garden: choose crops, generate a companion-placement guide, save it, then identify plants and return to their history.

The main pieces

  • GardenWorkspace.tsx connects visitor drafts, saved gardens, editing, replacement, and identification views.
  • The plan route calls the companion provider on the server. GardenMap.tsx renders the normalized placement guide with the real rectangular proportions.
  • Clerk provides user identity. The garden route and garden service save one owned garden in Neon through Prisma. Confirmed replacement clears old history and changes the revision.
  • PlantUpload.tsx prepares a temporary photo. Server identification routes normalize provider responses; history.ts saves confident results against the current garden revision.
  • Signed receipts let persistence retry without another provider request. Photos are not stored permanently.

Reference route: uncertainty stays out of history

The PRD confidence policy becomes the specification’s normalization contract, then an observable behavior.

Analyze a photo

A server-only request receives provider data.

→

Apply the policy

Valid name, boolean classification, score ≥90/100, and usable evidence.

→

Show the outcome

Confident results save to history. Uncertain results ask for another photo.

1. Decide what qualifies

src/lib/server/identification.ts → normalizeIdentification rejects missing names, invalid classification, nonnumeric/out-of-range scores, scores below 90, and missing usable botanical evidence. It does not substitute overallConfidence. The score is a provider score, not a calibrated probability.

2. Stop before persistence

src/app/api/identifications/route.ts → POST returns { outcome: "uncertain" } when normalization fails, before signing a result receipt or calling saveIdentification. Confident weeds and non-weeds both pass into saving.

3. Explain the outcome

src/components/PlantUpload.tsx → the uncertain outcome shows the clearer-photo prompt and explains that uncertain results are not saved.

Evidence: tests/identifications-route.test.ts, “does not save uncertainty and keeps provider failure distinct,” supplies a simulated score of 89 and asserts the save function was never called. Normalizer tests cover the threshold and invalid evidence. The completed learner simulation also produced no history entry. The final run after the UI refinements passed all 104 tests across 17 files, along with lint, typecheck, and the production build.

A practice to reuse

Before implementation, turn an uncertain API capability into an explicit acceptance rule with a failure case. Trace that rule through the PRD, technical contract, save boundary, focused test, and observed behavior. In Shamba AI, this kept a high-looking score from bypassing missing identification evidence and kept uncertainty out of saved history.

To change this, start here

  • Planning inputs: schemas.ts and GardenMap.tsx. Preserve the placement-guide boundary; do not invent capacity rules.
  • Confidence policy: the normalizer stop, shared schemas, receipt validation, PRD/spec, and their tests. Coordinate any future rule change across all of them.
  • Weed guidance: guidance.ts. Keep the narrow reviewed allowlist and fallback; changing it requires explicit review.
  • Replacement/history safety: gardens.ts and history.ts. Preserve ownership, revision checks, transactions, and retry idempotency.
  • Visual styling: globals.css and the component CSS Modules. motion.ts supplies the reduced-motion guard for GSAP animation.
